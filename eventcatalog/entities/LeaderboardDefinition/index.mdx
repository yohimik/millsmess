PostgreSQL owns settled scores, statistic revisions, season status and rewards. Core modules perform result settlement and projection ingestion. Redis is an optional live read projection; ClickHouse is analytical history. These databases are infrastructure, not additional application services.

## Real-time statistics versus final results

Media Engine produces SessionStatisticsReported at up to 1 Hz per bounded participant shard (128 players maximum). Each sample is cumulative and identified by session, shard, owner epoch and sample sequence. Core validates current ownership and registered metric definitions; newer samples replace older live overlays. Recovered engines restore cumulative statistics/watermarks or explicitly reset the overlay under the new epoch. Samples never increment settled totals and can be coalesced when lagging.

SubmitSessionResult comes only from the authoritative engine and carries a verified immutable result digest. PostgreSQL commits unique tenant/session/result revision, final totals, rating changes, affected leaderboard entries and outbox in one transaction. Remove that session's provisional overlays as part of the consistent read model transition. Core acknowledges only after commit. An engine waiting on settlement retains durable result intent before SessionEnded; a crash resumes finalization through reconciliation.

Stats metric definitions are game-maintainer configuration: identifier, unit/scale, signedness, bounds, aggregation (sum/max/min/latest), privacy and leaderboard eligibility. A client cannot submit arbitrary scores. A result correction is a privileged audited new result revision with replacement/recalculation semantics, never an extra additive win. Recompute affected player totals/rating in deterministic result order; frozen seasons require an explicit correction/reward compensation policy.

## Live leaderboard behavior

Boards are keyed by tenant, game-policy boardId, seasonId and regional/global scope. Score is a signed fixed-point integer string with an explicit scale. Sort by score in the board's direction, then playerId in bytewise ascending order. Rank is a deterministic **ordinal** starting at one; equal scores receive different ordinals through the tie break. Never use a floating-point compound score for timestamp/ID tie breaks.

Default target: a committed result appears in regional live reads and Socket invalidation within **2 seconds p99** under designed load. Live provisional statistics target **1 second p99** from engine sample acceptance. These are runtime acceptance targets, not measurements performed by this catalog. Responses include asOf, revision and stale. Global boards have a separate **5-second p99** target and expose federation watermarks. ClickHouse analytics target **10-second p99** visibility and must expose actual ingestion lag.

GetLeaderboard supports top-N and around-player pages (up to 100 rows), with an opaque cursor bound to tenant/board/season/sort key and a snapshot revision. Around-player and cursor modes are mutually exclusive. Snapshot pages expire after 30 seconds; expired/missing revision returns resync-required and restarts paging. This avoids duplicate/skipped rows under rapid score changes. SubscribeStatistics is connection-scoped and pushes coalesced LeaderboardUpdated invalidations at most once per second per board; clients fetch the latest page.

Redis projects absolute score + per-entry revision using an atomic compare-and-set script. Stale updates are ignored. Redis sorted sets store scores as doubles, so the full SignedValue range cannot safely be used as a numeric ZSET score. Use fixed-width sortable decimal encoding with sign/direction normalization and a lexicographic member including player ID, all numeric ZSET scores equal to zero, plus an index of current member per player; atomically replace only when revision advances. Alternatively restrict the board's scores to exactly representable integers or read PostgreSQL. Score encodings and tie behavior need conformance tests for negative values and ties before deployment.

Redis loss triggers rebuild from a consistent PostgreSQL snapshot at a watermark into a fresh namespace, followed by ordered outbox catch-up, then atomic namespace switch. Never flush the active board to rebuild in place. While degraded, serve bounded PostgreSQL indexed reads or return retryable-unavailable; do not advertise a stale cache as current. A single hot global board has a serialization/read-ranking bottleneck: scale with regional partitions and top-K merge for public top pages, or dedicated board authority partitions for exact around-player ranks.

## PostgreSQL and ClickHouse division

PostgreSQL schema responsibilities: result ledger unique by tenant/session/revision; player totals by tenant/player/season/metric; leaderboard entry keyed tenant/board/season/player with score and revision; board watermark; frozen season snapshot; reward idempotency; outbox/inbox. Use indexes matching board/season/score/player ordering. Serializable settlement or explicit ordered player row locks handle concurrent results, and deadlock/serialization retries rerun the complete transaction.

ClickHouse stores historical samples and result versions partitioned by event date and ordered by tenant/game/session/event semantic identity as appropriate for query patterns. A result projection is keyed by tenant/session/result revision; aggregate queries first select latest valid revision per result. ReplacingMergeTree background merges are not immediate uniqueness enforcement. Do not SUM raw at-least-once inserts or rely on background merges to make materialized sums correct. Choose explicit deduplicated queries (argMax/FINAL), a verified deduped staging path or periodic recomputation. This is especially necessary when a result correction replaces an earlier revision.

Core ingestion workers consume a dedicated statistics subscription, with separate batch, concurrency and connection pools from lease renewal/admission. A failed ClickHouse insert retries a stable batch identity; checkpoint ACK only after confirmed ingestion, but query-time semantic dedup remains mandatory. ClickHouse outage buffers within durable retention and alerts on lag; it never blocks a match, lease renewal, committed leaderboard or reward. Beyond retention, backfill from PostgreSQL result ledger and retained sample archive, stating any lost provisional history.

Global leaderboard authority is one declared home cluster per board. Regional Core services federate **settled results**, deduplicated by origin tenant/region/cluster/session/result revision, to that board home. A home partition delays global ranking but does not block regional matches. Source corrections replace prior contribution, not duplicate it. Global exact rank reads target the board home and expose its watermark; do not merge asynchronously replicated rank numbers. Cross-region result federation needs signed source identity and residency/consent rules.

## Seasons, abuse and operational tests

FinalizeSeason moves open to closing, stops assignment of new sessions to that season and records settleThrough. Wait for all eligible sessions to finish/fail and settle under an explicit operator deadline; abandoned outcomes get a declared policy rather than an invented zero score. Freeze a ranking snapshot and digest, mark finalized, then publish SeasonFinalized. Reward grants deduplicate tenant/season/player/reward. The next season gets a new ID and can accept sessions while the old closes.

Leaderboards enforce visibility, bans, anti-cheat and correction policy before settlement. Rate-limit around-player enumeration, avoid private identity in public entries and apply deletion/tombstone policy in every materialization. Required runtime tests: redeliver a result 100 times; reorder samples; kill Core after settlement before publish; lose Redis; delay ClickHouse; race two session results for the same player; correct a prior result; finalize with a late session; compare ties and near-limit signed scores; federate the same result twice. Authoritative totals/rewards must remain unchanged by delivery duplication.
